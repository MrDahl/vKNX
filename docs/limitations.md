# Known limitations (status 0.13.2, 2026-11-12)

**Decisive:** a successful build and self-test is *not* proof of ETS compatibility. Only what the owner has tried in ETS counts as confirmed.

## Confirmed in ETS 6.4.1 by the owner
- **Import, addressing and download** of push button, switch actuator, dimming actuator, slider push button, blind actuator and multisensor; devices on other areas and lines; partial downloads, also after a restart of vKNX (0.11.1).
- **Binary input, weather station and the alarm inputs of the blind actuator** working together over two lines with two couplers (2026-11-09).
- **Couplers:** addressing, download and the group filter table that ETS calculates; three lines (1.1, 1.2, 1.3) with downloads to all of them from one interface set to the main line (1.0).
- **KNX Data Secure:** secure commissioning of the secure push button and the secure switch actuator on three lines, secure group communication, and (0.13.2) that they keep their download when vKNX restarts.
- **Application version 5 (0.13.0):** group object names taken from the name parameters (`Output 1 - Bathroom lights: switch`, ETS text parameter reference with `{{0:unnamed}}`) on all products with named channels, and the blind key *Move at once*.
- **The interface** reports a stable maximum APDU length of 254. The group monitor "disconnect" noted in earlier versions was not a fault in vKNX (the changing APDU length, since fixed, and connecting/disconnecting in ETS by hand).
- **Windows:** the installer, the WebView2 window, the update button, rename, the floor plan with the scaled one-card symbols.

## Not confirmed in ETS one by one
The owner reported on 2026-11-11 that everything worked, also the new devices, but these were not named one by one. Treat them as probably fine, not as proven:
- **Room thermostat and heating actuator:** DPT 20.102 (operating mode), a signed 16 bit parameter, the control loop with PWM and monitoring. Model limits: the thermostat's room is a simple first-order model (4 K/h at full heating, time constant 3 h) and does not know about the heating actuator (the valve is assumed to follow the control value at once); a thermal valve drive's delay is not simulated; heating only (no cooling); the weather station cannot be changed from the card, only through ETS parameters.
- **Logic module and time master:** 32 input/output pages, 8 timer pages, 3 and 8 byte time objects, *Read on init*. It is **not an ETS plug-in**: the logic editor is a window inside the vKNX control panel.
- **Info display**, and its **light control screen** (application version 6, unreleased): new for ETS are parameters that hide the row parameters, 3 byte and 2 byte output objects. The wheel picks hue and saturation at full brightness; brightness is a separate object (as in the colour dimming actuator). No HSV, RGBW or XY objects.
- **Presence detector, colour dimming actuator and energy meter (new, unreleased): not tried in ETS at all.** New for ETS: objects of 3 bytes (DPT 232.600) and 4 bytes (DPT 14.056, 13.010, 13.013), DPT 7.600, 9.021 and 1.018. Behaviour is covered only by our own mini-ETS (`MoreProductsTest`). Model limits: the detector's movement and room brightness come from the card (no simulated people); once the light is on, every movement restarts the follow-up time whatever the brightness. The colour actuator keeps colour and brightness apart (the brightness objects never change the colour; the RGB status is the colour while on and black while off); no HSV, RGBW or XY objects, no colour scenes. The energy meter is one phase at 230 V with a purely resistive load (current = power / 230 V); its counter starts at 0 when vKNX starts; a dimmed lamp counts with its full power (the load inputs are 1 bit).
- **The installer's WebView2 step (0.13.1):** the setup contains Microsoft's WebView2 bootstrapper and runs it when the PC has no WebView2. Built and bundled by the release workflow, **not tried on a clean Windows 10** yet.
- **Coupler open points:** ETS may not set the x.y.0 address automatically for a line coupler (manual addressing is fine). Medium rule in ETS: a TP/TP coupler needs a TP main line or a TP backbone; it cannot sit between an IP line and a TP line (that needs an IP/TP router, not part of vKNX).
- **Non-Latin text in ETS parameters** (see device names below).

## Verified by our own tests (without ETS) [T]
About 30 test programs in `core/test` (run one with `tools/selftest.sh <Name>`): the mini-ETS `SelfTest`, `TunnelTest`/`TunnelLineTest` (real KNXnet/IP tunnel), `ProductsTest` and `NewProductsTest` (all products, partial download), `TopologyTest` and `CouplerTest`, `SecureTest`, `RenameTest`, `DownloadResumeTest`, `ResetSaveTest` (state after a master reset and after a forced stop), `GhostTest` (a removed device leaves the bus), `InstallationFileTest`, `AppTest`, and `KnxprodCheck` (the checked-in `.knxprod` files match `Products.java`; the release stops if they do not). **Only `SelfTest` and `KnxprodCheck` run in the release workflow**; the others are run by hand before a change is pushed. The control panel is checked with a headless Chromium against the running app, not in the WebView2 window.

## Control panel - what the wording means
- **Status wording:** "ETS / IP client connected" means the KNXnet/IP server reports an open connection. It does not prove that a download will succeed. "Interface ready" only means the server is running.
- **Download status** is derived from the load states of the device's four tables (empty / in progress / partial / complete / error). It says nothing about how far ETS is.
- **DPT decoding** uses the types declared in the product definitions. A group address used by devices with different types, or by none, is shown as "Unknown DPT" with raw data. Telegrams that ETS sends to addresses no device uses are therefore not decoded.
- **Device filter in the monitor** shows telegrams sent by the device or addressed to one of its configured group addresses. The second kind is not proof that the device received them.
- The monitor keeps the latest 3000 telegrams in memory; older ones are only in `vknx.log`.
- The floor plan can have up to 8 floors (each its own image); rooms and room filters are not part of this version. A channel can be placed once, on one floor.
- Touch screens have not been tried.

## Functional limits
- **Line routing (0.6.0).** With *Settings → Route telegrams between lines through couplers* switched on (default), a device only hears telegrams from another line if every coupler on the way exists with an x.y.0 / x.0.0 address and lets the telegram pass: group telegrams by *route / block / filter* (filter = the group address must be in the filter table that ETS downloaded), individually addressed telegrams by the physical setting ETS writes (filter = only towards the addresses behind the coupler), and the hop count is lowered by every coupler (7 = unlimited, 0 = telegram discarded). Switched off, the network is one flat line as before.
- **Modelling choices that are not from a standard:** (1) a coupler that has never been downloaded routes everything (factory state "route all", empty filter table); (2) an *unloaded* coupler keeps the routing bytes ETS wrote during the unload procedure (filter, empty table), so it blocks group telegrams but still passes individually addressed ones for its own subtree; (3) a coupler routes according to its stored settings even while the load state machine says "unloaded"; (4) broadcasts follow the broadcast bits of the physical setting; (5) the repeat, acknowledge and "routing counter" details of real couplers are not simulated; (6) there is no bypass for ETS: its traffic (addressing, programming mode, downloads) crosses couplers exactly like any other telegram, so couplers must be downloaded first (a factory-new coupler routes everything); (7) a coupler that gets an *unload* event falls back to filter with an empty table, whatever ETS wrote before.
- No building or environment simulation (only the thermostat's simple room model and the random values of the sensors); no ETS project import.
- The multisensor value and interval are set in ETS only; the panel just shows them.
- **Export / import (Settings → Share):** the file holds what is saved in the state of each device (address, download, parameters, logic circuit) plus the floor plan, layout and icons. It does **not** hold what is only live (lamp on/off, blind position, sensor values, the clock of the time master) or settings (interface line, theme); those start as after a restart. A file is only accepted by a vKNX with the same device layout (internal schema); if that changes in a later release, old files are refused with a clear message and must be exported again. Import replaces everything (the previous installation is saved as `backup-before-import.vknx`). The file contains secure devices' keys. The browser download is the standard one of the WebView2 window (it saves to the Downloads folder). Importing in ETS terms: the receiver sees the same simulation but, to change group addresses or parameters, needs the ETS project (not part of the file).
- Device names are free (40 characters). Text typed into ETS parameters (key, output and channel names) is stored by ETS in a fixed number of bytes: Western letters take one byte, other alphabets (if ETS stores them at all) several, so fewer characters fit; vKNX reads them as UTF-8 when possible and otherwise as ISO 8859-1. What ETS does with non-Latin characters in a text parameter has not been tried.
- **Products are built by hand:** the `.knxprod` files can only be made on Windows with ETS (`tools/make-knxprod.ps1`). After a change of `Products.java` they must be rebuilt and committed; `KnxprodCheck` stops a release where they were not.

## Design
- **Persistence:** every device writes its state file 3 seconds after something ETS did (a download, an address, a restart), within 30 seconds after other changes, and again when vKNX closes. A forced stop can lose the last few seconds of a download. Live values (lamp on/off, blind position, sensor values) are not kept.
- No login/isolation per student: each student runs their own local instance.
- Built for teaching only; no emulation of other manufacturers' firmware.
- The program is not code-signed, so Windows may show a SmartScreen warning; the first start asks for a firewall exception (UDP/TCP 3671).
- vKNX is not affiliated with KNX Association. It uses the open-source Calimero library with a few local patches (`third_party/patches`).

## KNX Data Secure (secure push button and secure switch actuator)
Secure commissioning, the secure download and secure group communication are **confirmed in ETS 6.4.1 by the owner** (three lines). Our own test (`SecureTest`, Calimero's secure client) covers: commissioning with the factory key (FDSK), replacing it with a tool key, writing a group key and the group object security flags, switching security mode on, authenticated and encrypted group telegrams, and that plain telegrams to a secured group object are ignored (local patch `calimero-core-secure-plain-drop.patch`).
Limits: no QR code and no `.knxkeys` file (the device certificate is shown as text, 36 characters); no secure management of couplers, no IP secure and no secure tunnelling (the interface uses plain tunnelling). Secure devices announce a maximum APDU length of 254 bytes. The FDSK is random per device and stored with its state; an exported installation file contains the keys.
